## 0. Рамка оператора (6 режимов — обязательна для round-4)

| # | Режим | Правило | В round-4 |
|---|---|---|---|

Четыре направления round-4 (мандат):

1. **Домен-адаптивная дистилляция** — масштабировать реальную часть корпуса
   (записи стора владельца — целевой домен памяти) с privacy-гейтами (§2).
   Основание: 8086/100k ≈ 8 % реальных данных в round-3; RU-доля корпуса
   41.9 % при квоте ≥40 % (prepare_dataset.py, training/README.md).
2. **Студент крупнее: 30M → 45–60M.** Два варианта с оценками:

| Вариант | Параметры | Оценка ONNX int8 | Бюджеты | Латентность |
|---|---|---|---|---|
| A (рекомендация) | ~45M | ~45–47 МБ — экстраполяция от измеренной точки 30.3M→29.6 МБ (≈1.0 байт/парам); измерить на этапе run | ≤60 МБ артефакт (nano-model-plan.md NM-1b), ≤95 МБ wheel — проходит | нет данных; измерить на этапе run (микробенч на том же хосте, что baseline-артефакт) |
| B | ~60M | ~60–62 МБ — та же экстраполяция; измерить | верхняя грань впритык к ≤60 МБ; wheel ≤95 МБ — проходит | нет данных; то же |

   **Вывод-рекомендация: вариант A (~45M).** Общий риск обоих вариантов:
   в окне 45–60M НЕТ готового pre-trained мультиязычного init — все
   проверенные кандидаты >100M (проверка HF API 2026-09-03,
   training/README.md «Кандидаты на init студента 45-60M»); rubert-tiny2
   (29.4M, MIT) остаётся единственным <100M init. Варианты A/B означают
   расширение архитектуры поверх rubert-tiny2-init → часть init будет
   без предобучения — feasibility-вердикт за АрхКомом (вопрос 5.1).
   Вне окна: `multilingual-e5-small` 117.7M → int8 ≈ 118 МБ — превышает и
   ≤60 МБ артефакта, и ≤95 МБ wheel (числа параметров — training/README.md;
   лимиты — nano-model-plan.md) — отпадает при канале «эмбеддер в main wheel»
   (ADR-0021 Stage 1).
3. **Кросс-лингвальная RU↔EN специализация.** Основание: translation-twins
   sens **0.00** на замороженном эмбеддере (layer-a-evalsets, цит. в
   calibration-b2p-prereg.md «Основание») — переводная пара записей не
   распознаётся геометрией. Механика: доля переводных/смешанных RU↔EN пар в
   корпусе (§2) + KD к MRL-учителю Qwen3 (нативно мультиязычен,
   training/README.md). Гейты — §3, g5.
4. **max_seq 256 → выше.** Граф статичен 1×256 (export_onnx.py); поднятие =
   ре-экспорт с новой статичной формой + снятие капа 256 токенов в
   dataset/prepare_dataset.py. Кандидаты: 384 / 512 (выбор — вопрос 5.4).
   Оценка роста инференса: абсолютных чисел нет (латентность не измерялась,
   Ограничения 1); механизм — attention-часть растёт ~квадратично по длине
   последовательности, линейные слои — от max_seq не зависят; измерить на
   этапе run до ратификации финального значения.

## 2. Корпус

- **Реальная часть** — стор владельца через `--from-mnemos-db`
  (read-only `file:…?mode=ro`, только поле `content`; теги/проект — только
  для фильтра; данные не покидают машину — training/README.md, политика
  приватности). **Privacy-гейты:** (1) данные стора никогда не попадают в
  репозиторий — в репу едут только fingerprint и счётчики (та же дисциплина,
  что round-3: fingerprint `b27f8cf0…` в manifest, тексты — нет); (2) явное
  разрешение владельца на выгрузку — вопрос 5.5; (3) при любом сомнении в
  записи — секрет-скан перед включением, отказ молча не глотается.
- **Целевые объёмы:** RU ≥ 40 % (действующая квота prepare_dataset.py);
  остальное EN. Цель по реальной части: **≥ 20 000 записей (PROPOSED —
  ≈2.5× к 8086 round-3)**; фактический потолок задаёт размер стора владельца
  на дату этапа corpus — синтезировать «реальность» запрещено; нижняя
  граница для валидности раунда — не меньше round-3 (8086).
- **Синтетическая часть — полная регенерация** новым учителем (если учитель
  сменится — тем более: вектора учителей несовместимы; даже без смены
  учителя регенерация обязательна из-за нового состава корпуса и seed-дисциплины
  seed=42, train/val 95/5 — prepare_dataset.py).
- **Fingerprint корпуса:** новый `dataset_fingerprint` (sha256 jsonl) в
  manifest кандидата — по механике export_onnx.py; fingerprint round-3
  (`b27f8cf0…`) сохраняется в отчёте для трассировки.
- **Замороженный holdout — НЕ трогать:** judged-корпус `c2ce056d…`
  (191 judged-запрос, BASELINE.md) остаётся фиксированным eval-набором
  no-harm: не расширяется, не переразмечается, не участвует в обучающем
  корпусе. Обязательная проверка этапа corpus: ассерт отсутствия пересечения
  текстов train-корпуса с текстами judged-корпуса (ранее не ассертился —
  добавить на этапе corpus; история round-3 по этому пересечению — нет данных).
- **Кросс-лингвальные пробы round-4** строятся НОВЫМИ синтетическими
  переводными парами на этапе corpus. Использовать holdout/evalsets кортекса
  (dataset-v4.2 и старше) для ОТБОРА эмбеддера запрещено — это утечка в
  запечатанный экзамен кортекса (holdout single-shot, data-contract §7).

## 4. Мера честности

- **Single-shot на запечатанном holdout после обучения.** Judged-корпус
  `c2ce056d…` не читается до завершения обучения кандидата; подбора порогов
  по результату нет — пороги §3 коммитятся до прогона и пинятся
  gate-контрактом (анти-HARKing, eval-methodology §6; sha256 контракта —
  в eval-отчёте).
- **Аддендумы — только ДО прогона.** Любое изменение §2–§3 после старта
  обучения = раунд аннулирован, корпус пересобирается, порядок с нуля
  (прецедент дисциплины: calibration-b2p-prereg §7.4, §8).
- **Run-log append-only** (data-contract §8): каждый прогон кандидата
  пишется с corpus fingerprint; повторный fingerprint = `RunLogRefusalError`.
- **Прогон выполняет TL** — с предварительными оценками wall-clock и RAM до
  запуска (RAM-перерасход = стоп-условие); фиксируются seed (42),
  версии torch/transformers, число потоков.
- **Вердикты ADOPT / REJECT — за АрхКомом+владельцем**, на отчёте с таблицей
  покрытия гейтов §3. Негативная дельта против baseline — расследование,
  никогда не merge; REJECT оставляет round-3 веса в проде (fingerprint
  `3b752e06…` не трогается, пины целы).
- Отчёт без provenance-цепочки (§0 режим 5) не рассматривается:
  «прогон без provenance = прогона не было».

## 5. Куплинг с vesma-cortex (обязательная секция)

Смена весов эмбеддера = новый `weights_sha256` = новый fingerprint
`nano:sha256:<new>`. По построению (не по договорённости):

1. **CORTEX-E-PIN:** vesma-cortex-v1 хранит пин
   `DEFAULT_EMBEDDER_PIN = nano:sha256:3b752e06…d84317ba` (stage2_run.py);
   ассерт `embedder_pin` при загрузке артефакта (inference-v1.md) даст
   `CORTEX-E-PIN` и отказ загрузки — калибровка кортекса на новом эмбеддере
   обязана быть пересобрана.
2. **Полный re-embed стора:** sweeper `heal_stale_embeddings` ре-эмбеддит
   все строки с чужим отпечатком, страницами, attempt-бюджет 200/тик
   (manager.py); окно миграции оценивать на этапе run (нет данных: длительность
   на объёме стора владельца не измерялась).
3. **Перекалибровка кортекса — фича `cos_target`:** распределение косинусов
   сдвинется; полоса [0.40; 0.55) корпуса v4.2 зафиксирована как «ограничение
   замороженного embedder», и в препреге прямо записано: «Требование смены
   полосы = смена эмбеддера, отдельное решение» (calibration-b2p-prereg §2).
   Round-4 — это и есть то решение: g4 (§3) даёт знаковую дельту, вердикт
   перекалибровки — волной cortex-recalib.
4. **Один поезд:** embed-round-4 и cortex-recalib едут вместе — движение
   весов эмбеддера в прод без готовой перекалибровки кортекса запрещено
   (потребитель откажется по пину или, что хуже, останется на старых весах).
5. **Re-baseline движка в том же PR:** S1m-гейт требует точного совпадения
   `model_fingerprint`; смена весов = RED с re-baseline `--record` в том же
   PR (ADR-0021 / BASELINE.md §11).
6. **Dual-provider (опция снижения риска, вопрос 5.6):** переходный период
   со старым и новым отпечатком параллельно (старые вектора живут до
   дозаполнения sweeper'ом, поиск не мигает). Требует движковой поддержки
   двух провайдеров — сейчас NanoProvider один на процесс; это движковая
   фича, в скоуп round-4 НЕ входит, решается отдельно до свапа.

## 6. Открытые вопросы владельцу/АрхКому

1. **Размер студента (бюджет):** вариант A ~45M (рекомендация, оценка ~45–47
   МБ int8) vs вариант B ~60M (~60–62 МБ, впритык к бюджету ≤60 МБ). Оба
   требуют расширения архитектуры без готового pre-trained init в окне
   (training/README.md) — АрхКом: принять init-риск или ограничить round-4
   корпусом на текущих 30M (против мандата лидерства).
2. **Учитель:** оставить Qwen3-Embedding-0.6B vs апгрейд. Рекомендация —
   оставить: по ресерчу nano-model-plan.md §8 Qwen3.8-линейка без эмбеддеров
   <27B, Qwen3.5-Embedding не выпускался, Qwen3-Embedding-0.6B — свежайший
   открытый мультиязычный (проверка MTEB-релизов 2026-08); смена учителя
   валидна только при новом верифицированном кандидате Apache-2.0/MIT.
3. **Размещение реестра модели:** карточка «embed-release-parity» — нужен ли
   эмбеддеру реестр по образцу cortex (ADR 0003: одна ревизия на main, теги
   `model-v1-<fp8>`, eval-results.json, MODEL_CARD, recall-процедура) вместо
   текущей раскладки `src/vesmaro/models/vesma-embed-v1/`. Рекомендация —
   да, паритет с cortex-реестром; вопрос АрхКому.
4. **max_seq:** финальное значение 384 vs 512 — после замера латентности на
   run-стенде (g6) и доли текстов, обрезаемых при 256 (измерить на этапе
   corpus; сейчас нет данных).
5. **Dual-provider переход (§5.6):** принимать ли движковую фичу
   параллельных провайдеров как условие свапа, или single-swap с окном
   sweeper-миграции. Рекомендация — dual-provider, если окно миграции по
   замеру > одного рабочего дня; иначе single-swap.
6. **Объём реальной части корпуса:** разрешение на выгрузку стора
   `--from-mnemos-db` для round-4 и фактический размер стора на дату corpus.

## 7. Что НЕ входит (анти-скоуп)

- **Сам прогон обучения/калибровки** — эксклюзив TL-сессии; этот документ —
  только контракт прогона.
- **Потребление MRL-голов 64/128/256 в рантайме движка** — отдельная
  движковая фича (срез + L2-ренорм на стороне провайдера); round-4 только
  измеряет пер-срезное качество (g3) и фиксирует `mrl_dims` в manifest.
- **Dual-provider в движке** — движковая фича, решение §6.5.
- **Смена ранжирующего стека** (hybrid_alpha, search v2) — вне раунда:
  S1m-числа между событиями несравнимы при смене стека (BASELINE.md,
  история re-baseline); round-4 сравнивается только с baseline 2026-09-15
  на неизменном стеке.
- **Внешние бенчмарки (MTEB)** — informational only, воротами не являются
  (ADR-0021 NM-0).
